# Архитектура Flutter-приложения

Практичная, модульная архитектура для Flutter-проектов с **Riverpod** и **GoRouter**. Основной принцип — **feature-first**: код конкретной функциональности находится рядом, а общие компоненты выделяются только при реальном переиспользовании.

Архитектура должна помогать разрабатывать приложение, а не увеличивать количество файлов и абстракций. Структуру можно расширять постепенно, по мере роста проекта.

## 2. Ответственность каталогов и правила владения

| Раздел | Назначение | Чего там не должно быть |
| --- | --- | --- |
| `app/` | Компоновка приложения | Сценариев отдельной фичи |
| `config/` | Роутер, тема, конфигурация окружения | Запросов к API, логики экранов |
| `core/` | Чистые, универсальные компоненты без знания бизнес-фич | `AuthService`, `OrderValidator` и прочего feature-кода |
| `shared/data/` | Общие API-клиенты, локальное хранилище, инфраструктура | Все репозитории приложения подряд |
| `shared/providers/` | Зависимости и состояние уровня приложения | Провайдеров каждого экрана |
| `shared/presentation/` | Общие виджеты, модальные окна и layout-компоненты | UI, специфичного для одной фичи |
| `features/<feature>/` | Собственная функциональность и её слои | Чужой реализации без явного контракта |
| `l10n/` | Ресурсы локализации | Бизнес-логики |

### `core/`

`core` следует делить по назначению: `constants`, `errors`, `extensions`, `formatters`, `validators`. **Не нужно создавать `core/utils` или `core/services` по умолчанию:** они легко превращаются в "свалку" для всего подряд.
Если действительно необходим общий технический сервис, поместите его в конкретную предметную папку, например `shared/data/connectivity/` или `shared/data/cache/`.

**Критерий для `core`:** код не зависит от отдельных фич, бизнес-сущностей и деталей доступа к данным. `EmailValidator` общего назначения может находиться в `core/validators`; проверка специфичного для оплаты промокода должна оставаться внутри `features/checkout/`.

### Разграничение `core`, `config`, `shared` и `features`

- **`core`** — независимые базовые правила и функции: обработка общих ошибок, расширения типов, форматирование.
- **`config`** — настройка приложения: маршруты, тема, окружения и параметры.
- **`shared`** — инфраструктура и компоненты, используемые несколькими фичами; могут зависеть от Flutter и сторонних пакетов.
- **`features`** — бизнес-функциональность. Репозиторий по умолчанию принадлежит фиче, даже если его результат читает ещё один экран.

Не переносите код в `shared` только потому, что есть вероятность его переиспользования. Перенос оправдан, когда появился реальный второй потребитель и определился понятный общий контракт.

## 3. Feature-first: каждая фича владеет своими слоями

Корневой каталог **`features/`**, представляет функциональные модули.

```text
features/
├── auth/
│   ├── presentation/
│   │   ├── screens/
│   │   ├── providers/
│   │   ├── widgets/
│   │   └── modal/
│   └── data/
│       ├── models/
│       ├── sources/
│       └── repositories/
├── users/
│   ├── presentation/
│   └── data/
└── settings/
    └── presentation/
```

Внутри `presentation`: `screens/` — самостоятельные страницы; `providers/` — Riverpod Provider/Notifier и состояние фичи; `widgets/` — локальные компоненты; `modal/` — `Dialog`, `BottomSheet` и другие модальные окна. Внутри `data`: `models/` — DTO/модели данных; `sources/` — конкретные API, базы, storage; `repositories/` — единая точка получения и обработки данных для потребителя.

Папки `sources/` может не быть: если репозиторий использует один простой API и слой источника не добавляет пользы, прямое обращение из репозитория допустимо. Аналогично модели не нужно дублировать без причины.

### Кому принадлежит общий репозиторий?

Не стоит размещать один `AuthRepository` и в `features/auth`, и в `shared/data`. У репозитория должен быть **один владелец**. Если авторизация — отдельная функциональность, реализация остаётся в `features/auth/data/`. Другие фичи получают информацию о текущем пользователе через узкий публичный контракт (`CurrentUserReader`, session provider или общий интерфейс), не импортируя внутренние экраны или Notifier авторизации.

Если данные образуют действительно общий самостоятельный модуль (например, общая сессия или настройки приложения), можно выделить его в `shared` либо в отдельную фичу с явно опубликованным API. Не перемещайте целый репозиторий в `shared` лишь из-за двух импортов.

### Взаимодействие фич

- Фича не должна напрямую менять внутренний `Notifier` другой фичи.
- Не импортируйте её приватные виджеты, `sources` и детали реализации репозитория.
- Для межмодульного взаимодействия используйте ограниченный публичный интерфейс, общий провайдер-контракт или навигацию с типизированными параметрами.
- Если возникает циклическая зависимость (`auth → users → auth`), вынесите общий контракт или модель в нейтральный модуль и проверьте границы ответственности.
- `shared` не зависит от `features`. `core` не зависит от `shared` или `features`.

**Не создавайте интерфейс для каждого класса.** Явный контракт нужен на действительной границе модулей, когда есть польза для разделения зависимостей, замены реализации или тестов.

## 4. Domain layer: необязательный слой

**В малых и средних приложениях отдельный `domain/` обычно не нужен.** Стандартная схема `presentation → repository → data source` часто полностью покрывает требования. Domain полезен, когда действительно нужно изолировать сложные бизнес-правила.

Рассмотрите `domain/`, если:

- есть сложные расчёты, бизнес-инварианты, правила доступа или офлайн-синхронизация;
- правила должны быть независимы от Flutter, API и хранения данных;
- бизнес-логика повторно используется несколькими сценариями;
- планируется значительное расширение, условно **более 10 фич**, либо есть подтверждённый план роста;
- отдельные бизнес-правила требуют изолированного тестирования.

**Число фич — сигнал пересмотреть архитектуру, а не автоматический триггер.** Проект с 15 CRUD-фичами может обходиться без `domain`, а проект с тремя сложными финансовыми фичами может нуждаться в нём сразу.

```text
features/orders/
├── presentation/
│   ├── screens/
│   ├── providers/
│   └── widgets/
├── domain/                          # Добавляется при необходимости
│   ├── entities/
│   ├── repositories/                # Контракты, если они нужны
│   └── services/                    # Бизнес-правила без инфраструктуры
└── data/
    ├── models/
    ├── sources/
    └── repositories/                # Реализации контрактов
```

### Use cases — не по умолчанию

**Не создавайте `GetUserUseCase` или `LoginUseCase`, если они только перенаправляют вызов репозиторию.** Use cases уместны, если прямо требуются ТЗ, архитектурными условиями или особыми требованиями к тестированию, либо если сценарий координирует несколько сервисов и содержит существенную логику. При этом высокая тестируемость сама по себе не требует use cases: репозитории, чистые сервисы и Riverpod Notifier можно тестировать напрямую.

### Где должна находиться бизнес-логика без domain?

- **Виджеты** — только представление и обработка пользовательских действий.
- **Notifier/Provider** — координация UI-состояний, запуск операций, пагинация, состояния загрузки/ошибки. Не размещайте там сложные расчёты и устойчивые бизнес-правила.
- **Repository** — получение, объединение, кэширование и преобразование данных из источников; простые операции над данными.
- **Чистые классы или сервисы фичи** — самостоятельные сложные правила, которые не обязаны превращаться в целый `domain/`. Например, `features/orders/services/order_pricing.dart`; при росте можно перенести в `domain/services/`.

### Типовой поток без domain

```text
Screen / Widget
      ↓
Riverpod Provider / Notifier
      ↓
Repository (при необходимости — сервис с правилами)
      ↓
Remote / Local Data Source (если выделен)
      ↓
API / Database / Storage
```

С domain зависимости выстраиваются через его контракты: `presentation → domain interface`, `data → domain interface`. Domain не должен импортировать Flutter UI или реализации API.

## 5. Riverpod: состояние и зависимости

Используем Riverpod для состояния, асинхронных запросов и dependency injection. Провайдер принадлежит **области ответственности**:

- `shared/providers/dependencies.dart` — глобальная инфраструктура (`Dio`, общие API-клиенты, storage).
- `shared/providers/app_providers.dart` — состояние приложения (например, тема).
- `features/auth/presentation/providers/` — состояние авторизации и провайдеры зависимостей auth.
- `features/users/presentation/providers/` — загрузка, пагинация и детали пользователя.

Пример общей зависимости:

```dart
@riverpod
Dio dio(Ref ref) {
  final client = Dio(BaseOptions(baseUrl: AppConfig.apiBaseUrl));
  ref.onDispose(() => client.close(force: true));
  return client;
}
```

Пример провайдера репозитория и асинхронной загрузки в фиче (импорты и `part` для генерации опущены):

```dart
@riverpod
UsersRepository usersRepository(Ref ref) {
  return UsersRepository(ref.watch(dioProvider));
}

@riverpod
Future<List<User>> users(Ref ref) async {
  return ref.watch(usersRepositoryProvider).getUsers();
}
```

Для пагинации, обновления и сложного жизненного цикла состояния используйте `AsyncNotifier` или соответствующий Notifier. Генератор [`riverpod_generator`](https://pub.dev/packages/riverpod_generator) желателен, но не обязателен.

**Локальное UI-состояние**, например `TextEditingController`, видимость блока или выбор вкладки в одном экране, оставляйте в `StatefulWidget` или `flutter_hooks`. Не создавайте глобальный Provider на каждый boolean.

Избегайте прямой связи между внутренними Notifier разных фич: провайдер другой фичи может читаться через публичный контракт, но внутреннее состояние должно изменяться владельцем.

## 6. Экраны, виджеты и модальные окна

**Экраны** собирают UI и связывают его с состоянием, но не делают HTTP-запросы напрямую и не содержат сложных бизнес-правил.

**Виджеты** именуются по смыслу: `EmailTextField`, `LoginButton`, `UserListItem`. Названия вроде `CustomWidget` неинформативны; `AppButton` оправдан, если это действительно общий элемент дизайн-системы.

```text
features/auth/presentation/modal/
├── forgot_password_dialog.dart
└── forgot_password_sheet.dart
```

В `shared/presentation/modal/` размещаются только общие для нескольких фич модальные интерфейсы. Не выносите компонент в shared заранее: локальное расположение обычно проще в поддержке.

## 7. Роутинг

Для навигации используется `go_router`:

```text
config/router/
├── app_route.dart     # Описание маршрута (при необходимости)
├── routes.dart        # Имена и пути маршрутов
└── router.dart        # Конфигурация GoRouter
```

```dart
abstract final class Routes {
  static const splash = '/splash';
  static const home = '/';
  static const login = '/login';
  static const userDetail = '/users/:id';
}
```

```dart
@riverpod
GoRouter router(Ref ref) {
  final router = GoRouter(
    initialLocation: Routes.splash,
    routes: [
      GoRoute(
        path: Routes.splash,
        builder: (context, state) => const SplashScreen(),
      ),
      GoRoute(
        path: Routes.home,
        builder: (context, state) => const HomeScreen(),
      ),
      GoRoute(
        path: Routes.userDetail,
        builder: (context, state) => UserDetailScreen(
          id: state.pathParameters['id']!,
        ),
      ),
    ],
    errorBuilder: (context, state) => ErrorScreen(error: state.error),
  );
  ref.onDispose(router.dispose);
  return router;
}
```

Если в приложении несколько вкладок со своим стеком навигации, используйте `StatefulShellRoute.indexedStack` и общий `NavigationLayout`. Если вкладок нет — не усложняйте роутер.

`AppRoute` как отдельная обёртка не обязателен: добавляйте его, только если он действительно упрощает типизацию путей, параметров и переходов.

## 8. Тема

Тема остаётся в `config/theme/`. Центральное определение цветов, типографики и компонентов позволяет обеспечить единый визуальный стиль.

```dart
enum ThemeType { light, dark }

extension ThemeTypeX on ThemeType {
  ThemeMode get mode => switch (this) {
    ThemeType.light => ThemeMode.light,
    ThemeType.dark => ThemeMode.dark,
  };
}
```

```dart
abstract final class AppTheme {
  static ThemeData get light => ThemeData(
    useMaterial3: true,
    brightness: Brightness.light,
  );

  static ThemeData get dark => ThemeData(
    useMaterial3: true,
    brightness: Brightness.dark,
  );
}
```

Если пользователю нужно переключение темы, его состояние можно хранить в глобальном Riverpod-провайдере. Для небольшого приложения обычно достаточно стандартного `ThemeData` и `ColorScheme`, без собственной сложной системы классов.

## 9. Локализация

Переводы размещаются в `lib/l10n/`, например:

```text
l10n/
├── app_en.arb
└── app_ru.arb
```

Используйте стандартный `flutter_localizations` и `gen_l10n`. Тексты UI не должны быть разбросаны по коду. Для неподдерживаемых языков можно настроить fallback на английский.

## 10. Тестирование

Тесты определяются рисками и требованиями проекта. Структуру тестов удобно повторять за `lib/`:

```text
test/
├── core/
├── shared/
│   └── data/
└── features/
    ├── auth/
    │   ├── presentation/
    │   └── data/
    └── users/
        ├── presentation/
        └── data/
```

- **Unit tests:** форматтеры, валидаторы, репозитории, чистые бизнес-сервисы, Notifier.
- **Widget tests:** загрузка, ошибки, действия пользователя, различные состояния интерфейса.
- **Integration tests:** важные сценарии пользователя и реальное взаимодействие модулей.

Riverpod позволяет подменять зависимости через `ProviderContainer` или `ProviderScope` с `overrides`. Для тестируемости **не нужно** автоматически добавлять `domain`, интерфейс к каждому репозиторию и слой `use_cases`.

## 11. Правила развития проекта

1. **Feature-first:** новые функции размещаются в `features/<feature>` с собственными `presentation` и, при необходимости, `data`.
2. **Слои не смешиваются:** `data` не кладётся внутрь `presentation`; доменное поведение не смешивается с виджетами.
3. **Один владелец:** каждый репозиторий, провайдер и бизнес-сервис должен иметь понятный модуль-владелец. Избегайте дубликатов в `shared` и фиче.
4. **Публичные границы:** фичи взаимодействуют через узкие контракты и не меняют внутренние Notifier друг друга.
5. **Нет папки `helpers/`:** технические функции получают предметные названия в `core` или внутри своей фичи; `utils/` и `services/` не создаются как свалка.
6. **Domain необязателен:** рассматривайте его по сложности правил, планируемому росту и тестируемости; 10+ фич — ориентир, не жёсткое правило.
7. **Use cases — исключение:** нужны при содержательных сценариях, специальных требованиях к тестированию или прямом указании ТЗ, а не для каждого вызова репозитория.
8. **Notifier — не вся бизнес-логика:** состояние UI хранится в Provider/Notifier, самостоятельные правила — в репозитории или отдельных чистых классах и сервисах.
9. **`shared` — только после реального переиспользования:** не делайте код глобальным на будущее и не заставляйте `shared` зависеть от `features`.
10. **Папки только по необходимости:** не создавайте заранее пустые слои и абстрактные интерфейсы.
11. **Правильное направление зависимостей:** `core` независим от модулей, `shared` не импортирует фичи, UI не зависит от конкретных деталей API в виджетах.
12. **Пересматривайте границы:** рефакторинг структуры по мере роста лучше, чем изначально тяжёлая система ради гипотетических сценариев.

## 12. Какой вариант выбирать

| Размер / особенности | Рекомендуемый подход |
| --- | --- |
| Малый проект, 1–3 простые фичи | `features/<feature>/presentation` и только необходимые `data`; без `domain` |
| Средний проект, несколько независимых фич | `features/<feature>/{presentation,data}` и общий `shared` для реально переиспользуемой инфраструктуры |
| Планируется рост до 10+ фич | Та же структура, более строгие контракты модулей; рассмотреть `domain` там, где нужны самостоятельные правила |
| Сложные бизнес-правила, автономные расчёты, офлайн-синхронизация | Добавить отдельные чистые сервисы или `domain` внутри соответствующих фич |
| Специальное требование ТЗ к use cases | Добавлять `use_cases` адресно, без шаблонного дублирования методов репозитория |

**Итог:** рекомендуемая модель — **feature-first + Riverpod + repository pattern + чёткий `core` + компактный `shared`**. `features` группирует функциональность, `presentation` отвечает исключительно за UI, `data` — за доступ к данным; `domain` и `use_cases` остаются осознанными необязательными инструментами.
